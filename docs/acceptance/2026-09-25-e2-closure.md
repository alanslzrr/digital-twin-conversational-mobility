# E2 — cierre del control conversacional

Fecha: **25/09/2026**. Estado: **CERRADO en la rama de implementación**.
Siguiente entrega: **E3 — continuidad y recuperación de ingestión**.

## Criterio vigente

El usuario sustituyó la exigencia de una campaña de consumo real por el flujo:
**se alcanza el límite → pausa y aviso → aprobar continúa / rechazar detiene**.
No es necesario gastar 100.000 tokens de entrada ni 10.000 de salida para probarlo.
Esos valores son umbrales configurados, no un objetivo de consumo de prueba.

Este criterio sustituye la condición anterior de cierre de E2 mediante T01–T13
con modelo real y la prohibición de renovar ventanas del chat por aprobación.
No sustituye la aceptación global de movilidad, no autoriza gasto y no certifica
precisión semántica de un modelo que no se ha ejecutado.

## Implementación entregada

- **Modo interactivo predeterminado:** usa el gate de sesión nativo de EVE 0.65.0.
  La UI oficial muestra Approve/Stop; la decisión corresponde al usuario. Aprobar
  renueva la ventana sin borrar uso acumulado; rechazar cancela el turno sin borrar
  historia. No se introdujo una UI alternativa ni aprobación automática.
- **Sin bloqueo de campaña en el chat:** el transporte interactivo no pide reservas
  del ledger ni hace una llamada adicional a `input_tokens`. Era necesario separar
  ambos modos: de lo contrario, Approve podía continuar bloqueado por la campaña.
- **Campaña experimental opt-in:** `MOBILITY_BUDGET_MODE=campaign` conserva el ledger
  duradero, límites no renovables y las correcciones de exceso/concurrencia.
  `interactive` es el valor predeterminado; otros valores fallan cerrado.
- **Medición conservada:** eventos numéricos por intento HTTP (incluidos reintentos
  y compactación), turno y sesión; input/output/cache reportados, latencia, tamaño
  de contexto y pasos. Uso ausente sigue siendo `null`, no cero; cache no se suma
  nuevamente al input. El reporte SQL corresponde exclusivamente a campañas.
- **Protecciones conservadas:** Better Auth y propiedad/registro de sesión en Core,
  modelo fijo `gpt-6-luna` directo, `store:false`, endpoint permitido, límites de
  payload/respuesta, 2.048 tokens máximos por intento y deadline de 60 segundos.
  Límites de herramientas/búsquedas y preservación de evidencia siguen activos.
- **Compactación:** cápsula acotada conserva datos originales y correcciones;
  checkpoints sintéticos no se promueven a evidencia. No se afirma que una
  prueba determinista certifique la calidad de todos los resúmenes de un modelo.

| Comprobación | Resultado |
| --- | --- |
| `pnpm check` estándar, checkout aislado, Node 24.21 | Aprobado: lint, tipos, **189 pruebas**, builds Core/Web con Turbopack; Core cache hit, Web ejecutado |
| `pnpm test:budget:db` | **17 aprobadas** en esquema PostgreSQL aleatorio temporal eliminado al finalizar |
| Contrato nativo EVE instalado | **3 aprobadas**, incluidas dentro de las 189: umbral input, umbral output, rechazo |

| `pnpm build:agent` aislado | Aprobado; salida EVE generada únicamente en el checkout temporal |

La prueba del harness nativo carga la distribución instalada solo desde tests,
inyecta uso sintético en su estado, comprueba que no hay continuidad sin respuesta
válida y ejercita ambos botones. No simula una respuesta humana aprobatoria en
producción ni modifica internals de EVE. No es una prueba E2E de navegador.
Las pruebas de transporte usan fetch simulado; no se enviaron peticiones al modelo.

## Entrega y siguiente paso

E2 queda cerrado sin campaña real adicional. E3 puede comenzar directamente:
registro de intentos de ingestión, heartbeat y recuperación con pruebas sin gasto.

No se hizo push, merge en main, migración de la base habitual, activación de campaña
ni reinicio del runtime habitual. El cierre de implementación no equivale a su
activación; la transición operativa está documentada en [runtime local](../local-runtime.md#control-conversacional-e2).
