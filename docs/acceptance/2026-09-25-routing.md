## Cambio y contrato

- La regresión F01 se escribió y ejecutó antes de cambiar el adaptador: esperaba `available` y recibía `unavailable`. El fixture reproduce el error GraphQL `Direct modes must not be empty.`; los itinerarios de tests están identificados como sintéticos y nunca se usan en runtime.
- Política de dominio: TRANSIT exige un tramo de transporte público y permite caminar para acceso, egreso y transbordos bajo el límite total; WALK permite itinerarios íntegramente peatonales; TRANSIT+WALK permite ambas alternativas.
- Mapping OTP: `direct: [WALK]` siempre no vacío, `transitOnly` para TRANSIT y `directOnly` para WALK; acceso, egreso y transferencia WALK explícitos. Filtrado defensivo de modos, minutos a pie y transbordos tras la respuesta.
- El esquema del OTP **2.10.0 instalado** confirmó esos campos y los códigos de routing. La [documentación primaria de PlanModesInput](https://docs.opentripplanner.org/api/dev-2.x/graphql-gtfs/types/PlanModesInput) es referencia complementaria; no se asumió compatibilidad únicamente a partir de documentación de desarrollo.
- Razones estables distinguen entrada inválida, modos no soportados, lugar desconocido, período/cobertura, manifest ausente o incompatible, configuración, timeout, transporte, contrato GraphQL, payload y backend. HTTP 200 con errores GraphQL nunca se interpreta como ausencia de rutas.
- Solo códigos OTP permitidos cruzan el adaptador; no se devuelven mensajes arbitrarios del proveedor ni detalles de DB/rutas locales. Se mantiene el límite de 10 s y no se añaden reintentos ni redirecciones.
- Se mantienen horarios previstos, `realtimeApplied: false` y `accessibilityGuaranteed: false`. `no_route` significa que la búsqueda acotada no produjo itinerarios admitidos, no una demostración exhaustiva sobre toda la red: se solicitan cinco candidatos y se devuelven hasta tres tras filtrar.

## Verificación ejecutada

- `pnpm exec vitest run apps/mobility-core/src/routing.test.ts`: regresión roja antes del fix y verde después.
- Suite ampliada: **69 pruebas nuevas** (61 del adaptador y 8 de política de dominio). Incluye modos, límites exactos/cero, wheelchair, instantes con offset/cambio horario, validación, calendario, manifest, DB, transporte/timeout, GraphQL, payload, códigos OTP y compatibilidad de salidas previstas.
- `pnpm check`: lint y límites arquitectónicos, tipos, **143 pruebas / 16 archivos**, builds. Turbo reutilizó los resultados sin cambios de EVE; el build de Core se ejecutó. No se ejecutó `build:agent`, porque no cambió la implementación EVE.
- Core recién compilado servido temporalmente en **127.0.0.1:3011**, con autenticación MCP existente y OTP/Postgres locales reales. No se eludieron scopes ni se modificaron cuentas. El proceso temporal se detuvo al terminar; no se reinició el runtime habitual ni se reconstruyó el grafo.
- `node scripts/smoke-routing.mjs --port=3011 --at=2026-09-25T08:08:58.823Z`: **11/11 casos** con el instante original.
- `node scripts/smoke-routing.mjs --port=3011`: **11/11 casos** con hora actual de ejecución.
- `node scripts/smoke-routing.mjs --port=3011 --at=2026-09-26T18:00:00+02:00`: **11/11 casos** con sábado por la tarde dentro del calendario.

Resultados de las tres baterías: TRANSIT Atocha→Chamartín y vuelta devuelve tres itinerarios previstos de 780 s; TRANSIT+WALK también devuelve rutas. WALK Atocha→Chamartín con 15 min devuelve `no_route`; el control positivo WALK Atocha→Sol con 60 min devuelve un itinerario de 1.554 s. Cero minutos a pie, cero transbordos y wheelchair no provocan errores de contrato. La opción wheelchair no certifica accesibilidad operativa.

Los otros tres casos rechazan CAR, lugar desconocido y fecha fuera de calendario con su razón específica. No hubo llamadas al modelo, benchmarks ni despliegues. Las consultas MCP renovaron la ventana normal de actividad; esta batería **no** prueba inactividad ni suspensión.

- `data/validation/routing-2026-09-25T08-48-11-252Z/result.json` — instante original.
- `data/validation/routing-2026-09-25T08-48-12-287Z/result.json` — hora actual.

Los informes registran commit base y working tree dirty, hashes de fuentes locales, manifest, entradas/resultados, instantes y duración de cada caso. Los hashes describen el checkout del cliente, no una atestación remota del build servido. La validación se hizo arrancando explícitamente el build nuevo. Las ejecuciones preliminares de nueve casos se conservan, pero las tres baterías anteriores son la evidencia final.

Después de esas baterías se añadió una regresión adicional para timeout durante la lectura del body: algunos transportes lanzan `AbortError` en lugar de `TimeoutError`. El adaptador comprueba también la señal de deadline. Ese endurecimiento se verifica offline en la suite de 143 pruebas; no se atribuye a las baterías vivas anteriores ni modifica el mapping probado.

## Repetición y siguiente paso

No arranca/reinicia servicios, no modifica cuentas ni llama al modelo. Un caso positivo sin rutas falla; no se degrada a éxito silencioso. La evidencia se escribe con permisos 0600 bajo `data/validation/`.
